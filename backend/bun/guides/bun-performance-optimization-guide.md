# Bun Performance Optimization Guide

## Introduction

Bun is fast out of the box: a JavaScriptCore engine, a Zig runtime core with native I/O, and a bundler that turns source trees into single binaries. But raw platform speed is not the same as application performance. A Bun server can still stall on a slow JSON parser in a request handler, leak memory through an unbounded cache, or ship a 40 MB bundle that takes a second to start. Performance in Bun is engineered, not inherited.

This guide gives you a complete, repeatable methodology for making Bun applications fast: measure, profile, optimize, and verify. It goes far beyond the single profiling step found in general production guides. You will learn how to establish a trustworthy benchmark baseline with `bun test --bench` and load-testing tools, how to read CPU and heap profiles generated by `bun --cpu-prof` and `bun --heap-prof`, how to tune `Bun.serve()` for throughput and latency, how to shape the production bundle with `bun build`, how to cut startup time with lazy loading and compiled binaries, and how to keep the gains permanent with CI regression gates.

The target reader is a developer who already ships Bun applications and wants the next level of discipline around speed and memory. Every practice in the Best Practices section is demonstrated concretely in the Implementation Steps.

## Best Practices

### 1. Measure before you optimize

Optimizing without a baseline is guessing. Before changing anything, capture numbers you can trust: micro-benchmarks with `bench()` from `bun:test` for isolated hot spots, and realistic load tests with tools such as `oha`, `wrk`, or `autocannon` for end-to-end behavior. Record percentiles — p50, p95, p99 — plus throughput and peak RSS, not just averages. Averages hide tail latency, and the tail is what users feel.

```bash
# Baseline load test against a local server (keep-alive, 100 concurrent connections)
oha -z 30s -c 100 http://localhost:3000/api/items
```

Keep the baseline written down (a file in your repo is best) so every subsequent optimization answers one question: did this change move the numbers, and by how much?

### 2. Profile with the built-in profilers

Profiles beat intuition. Bun ships a CPU profiler and a heap profiler out of the box, plus the `bun:jsc` module for engine-level introspection. When a route feels slow, capture a CPU profile and look at the actual frames; when memory grows over time, capture heap snapshots before and after a soak cycle and diff them. The `bun:jsc` API exposes `heapStats()` for heap summary, `memoryUsage()` for RSS and engine memory, and `captureHeapSnapshot()` for full snapshots you can load into a heap analyzer.

```bash
# CPU profile: writes bun-profile-<timestamp>.cpuprofile in the current directory
bun --cpu-prof run src/index.ts

# Heap profile: useful for finding alloc-heavy phases
bun --heap-prof run src/index.ts
```

```typescript
// Engine-level memory introspection at runtime
import { heapStats, memoryUsage } from 'bun:jsc';

setInterval(() => {
  const stats = heapStats();
  console.log('Live objects:', stats.objectCount);
  console.log('Heap size (bytes):', stats.heapSize);
  console.log('RSS (bytes):', memoryUsage().rss);
}, 30_000);
```

Investigate what the profile says, not what you assume. The most common surprise is that the slowest frame is a standard library call in an unexpected location — which changes the fix completely.

### 3. Prefer native Bun APIs

Bun implements its I/O and server primitives natively, and they are the fastest path on the platform. Use `Bun.file()` and `Bun.write()` for file I/O, streaming APIs for large payloads, and `bun:sqlite` for local database access. When you import Node compatibility layers (`node:fs`, `node:http`, Express-style abstractions) you pay for translation work that the native surface does not.

Equally important: run in production mode. Bun enables development conveniences — hot reload hooks, dev-mode checks, verbose errors — when `NODE_ENV` is not `production`. Set it in your deployment environment, and Bun skips the dev-only work automatically.

```bash
NODE_ENV=production bun run src/index.ts
```

### 4. Design for memory efficiency

Bun's garbage collector handles allocation churn well, but it cannot fix unbounded growth. The patterns that keep a Bun process healthy over days of uptime are:

- Use prepared statements and WAL mode with `bun:sqlite` instead of parsing SQL strings repeatedly.
- Stream large payloads end to end instead of buffering whole objects in memory.
- Bound your caches — an unbounded `Map` used as a cache is a slow leak, not a fast optimization.
- Use `WeakRef` and `FinalizationRegistry` for caches keyed by objects with a natural lifecycle.
- Deploy low-memory containers with `--smol`, which tunes JavaScriptCore to favor lower memory usage over peak throughput.

```typescript
// Cache with a bound size — evict oldest entries instead of growing forever
const MAX_CACHE = 10_000;
const cache = new Map<string, unknown>();

export function memoize<T>(key: string, compute: () => T): T {
  if (cache.has(key)) return cache.get(key) as T;
  const value = compute();
  cache.set(key, value);
  if (cache.size > MAX_CACHE) {
    const oldest = cache.keys().next().value;
    if (oldest !== undefined) cache.delete(oldest);
  }
  return value;
}
```

### 5. Keep hot paths clean

A request handler runs thousands of times per second; every hidden cost multiplies. Common hot-path taxes include regexes recompiled per call, string concatenation in loops, synchronous I/O inside an async handler, and repeated `JSON.parse`/`JSON.stringify` of the same payload. Precompile regexes at module scope, prefer array joins or template literals over `+=` in loops, and parse request bodies once per request, not once per field access.

```typescript
// Precompile once at module scope — do not build the regex inside the handler
const ROUTE_PATTERN = /^\/items\/([a-f0-9-]{36})$/;

export function parseItemRoute(path: string) {
  const match = ROUTE_PATTERN.exec(path);
  return match ? match[1] : null;
}
```

### 6. Tune the runtime deliberately

JavaScriptCore defaults are good for the average workload; edge cases need explicit tuning, and only after profiling shows a real problem. `--smol` trades throughput for a smaller memory footprint. `heapStats()` from `bun:jsc` tells you whether memory is genuinely growing or merely allocated. When you find a true leak, fix the retention (cache, closure, stream not consumed) instead of masking it with a larger heap. Never raise a limit to silence a memory warning without knowing what is retaining the objects.

### 7. Optimize the HTTP layer

`Bun.serve()` is the fastest way to serve HTTP from Bun, and its options map directly to performance levers:

- `idleTimeout` controls how long keep-alive connections stay open — tune it to your traffic pattern instead of closing connections prematurely.
- `reusePort` enables `SO_REUSEPORT`, letting multiple processes share one port and spread load — pair it with multiple processes but never exceed the cores you have.
- `maxRequestBodySize` protects the server from oversized payloads; keep it slightly above your largest legitimate request.
- Stream responses for large bodies, and compress text responses with `CompressionStream` rather than buffering the whole payload.
- Keep the event loop unblocked: no synchronous I/O inside `fetch`, no heavy computation without yielding.

```typescript
import { CompressionStream } from 'node:stream/web';

const server = Bun.serve({
  port: 3000,
  reusePort: true,
  idleTimeout: 30,
  maxRequestBodySize: 10 * 1024 * 1024,
  async fetch(req) {
    const url = new URL(req.url);
    if (url.pathname === '/api/report') {
      // Stream a large generated payload with on-the-fly compression
      const { readable } = generateReportStream();
      const compressed = readable.pipeThrough(new CompressionStream('gzip'));
      return new Response(compressed, {
        headers: { 'Content-Type': 'application/json', 'Content-Encoding': 'gzip' },
      });
    }
    return new Response('Not found', { status: 404 });
  },
});
```

### 8. Shrink and shape the bundle

Bundle size affects startup time, memory, and deploy payloads. `bun build` enables tree shaking by default; make the rest explicit: `--minify` for smaller output, `--splitting` to share chunks across entry points, `--drop=console,debugger` to strip debug statements, and `--external` to keep native or huge dependencies out of the bundle when appropriate. For server applications, compile to a single standalone binary with `--compile` — Bun embeds the runtime and bytecode, eliminating install steps and shrinking cold-start latency.

```bash
# Production server bundle: tree-shaken, minified, single binary
bun build src/index.ts --compile --minify --bytecode --target=bun -o server
```

```text
# Bundle comparison for the same application
| Strategy                | Output size | Startup time (p50) |
|-------------------------|-------------|--------------------|
| tsx source run          | -           | 152 ms             |
| bun build (minified)    | 2.1 MB      | 84 ms              |
| --compile --bytecode    | 41 MB       | 39 ms              |
```

### 9. Cut startup time

Startup latency matters for CLI tools, serverless cold starts, and rapid horizontal scaling. The levers are: lazy `import()` for rarely used modules, modules free of top-level side effects, fewer dependencies on the entry path, inlined environment via `--env`, and a compiled binary. `bun --preload` can eagerly load small hot modules, but the bigger win is almost always removing work from the entry path rather than adding more of it.

```typescript
// Defer the heavy analytics client until it is actually used
const { AnalyticsClient } = await import('./analytics-client.ts');

export const analytics = {
  async track(event: string, data: unknown) {
    const client = new AnalyticsClient();
    await client.send(event, data);
  },
};
```

### 10. Gate regressions in CI

Speed is a feature, and features need regression tests. Run `bun test --bench` in CI with thresholds: a merge that makes the p95 worse than the recorded baseline by more than a few percent should fail the pipeline. The same goes for bundle size budgets and, where feasible, cold-start budgets. When every optimization is verified against a tracked baseline, performance stops being anecdotal and becomes engineering.

## Implementation Steps

### Step 1: Establish a Benchmark Baseline

Create a benchmarks directory with `bench()` cases for your critical paths. Keep them focused and stable: same machine class, warm-up runs, enough iterations to converge.

```typescript
// benchmarks/items.bench.ts
import { bench, run } from 'bun:test';

const sample = Array.from({ length: 100 }, (_, i) => ({
  id: `item-${i}`,
  price: i * 1.5,
}));

bench('serialize item list', () => {
  JSON.stringify(sample);
});

bench('parse item payload', () => {
  JSON.parse(JSON.stringify(sample));
});

await run();
```

```bash
bun test --bench benchmarks/items.bench.ts
```

Record the output — operations per second and p50/p95 latencies — into a `PERFORMANCE.md` baseline file in the repo. Then run one real-world load test so the micro-benchmarks have context:

```bash
oha -z 30s -c 100 -m GET http://localhost:3000/api/items > baseline-oha.txt
```

Save `baseline-oha.txt` too. From now on, every optimization is judged against this file.

### Step 2: Profile CPU and Find the Hot Path

Run the server under the CPU profiler, generate traffic for a couple of minutes, then stop it and open the `.cpuprofile` file in a flame-graph viewer (the Chrome DevTools Performance tab works well).

```bash
bun --cpu-prof run src/index.ts &
# generate load while it runs
oha -z 60s -c 200 http://localhost:3000/api/items
kill %1
```

Read the profile top-down: the widest frames at the top of the flame graph are where the CPU time actually goes. Look for three signatures:

- A wide standard-library frame in an unexpected location — your data shape is fighting the API (e.g., repeated parsing or unbounded regex use).
- A wide application frame — your own algorithm is the bottleneck; optimize the algorithm, not the runtime.
- Many thin frames of allocation — the workload is alloc-heavy; see the memory step before changing algorithms.

Whatever you find, write it next to the baseline. The profile is the evidence; the fix comes after.

### Step 3: Profile Memory and Detect Leaks

Start the server with a known workload, capture a heap snapshot, run a soak cycle, and capture a second snapshot. Compare the two to find what is retained.

```typescript
// scripts/snapshot.ts — capture a heap snapshot on demand
import { captureHeapSnapshot, heapStats } from 'bun:jsc';

const targetPath = process.argv[2] ?? './heap.heapsnapshot';
captureHeapSnapshot(targetPath);
console.log('Snapshot written to', targetPath);

const stats = heapStats();
console.log('Live objects:', stats.objectCount, '| Heap size:', stats.heapSize);
```

```bash
bun scripts/snapshot.ts ./before.heapsnapshot
# run the soak workload (e.g., 100k requests with varied payloads)
oha -z 120s -c 150 http://localhost:3000/api/items
bun scripts/snapshot.ts ./after.heapsnapshot
```

Load both snapshots into a heap analyzer and diff the retained objects. Repeated entries of the same class, event listeners, or stream objects point at the retention source: a cache without eviction, a subscription never cleaned up, a stream never consumed. Fix the retention, not the heap size. A flat RSS over a long soak is a healthy process.

### Step 4: Tune the HTTP Server

Apply the `Bun.serve()` configuration that matches your traffic: `reusePort` when you run multiple processes, an `idleTimeout` that lets real clients reuse connections, a sensible `maxRequestBodySize`, and streaming plus compression for large responses.

```typescript
// src/server.ts
import { BunFile } from 'bun';

const server = Bun.serve({
  hostname: '0.0.0.0',
  port: 3000,
  reusePort: true,
  idleTimeout: 30,
  maxRequestBodySize: 10 * 1024 * 1024,
  websocket: {
    perMessageDeflate: true,
  },
  async fetch(req: Request) {
    const url = new URL(req.url);

    if (url.pathname === '/api/items') {
      const items = await loadItems();
      return Response.json(items);
    }

    if (url.pathname === '/static/app.js') {
      // Serve a static file through the zero-copy path
      const file: BunFile = Bun.file('./dist/app.js');
      return new Response(file);
    }

    return new Response('Not found', { status: 404 });
  },
});

console.log(`Listening on http://${server.hostname}:${server.port}`);
```

Re-run the load test from Step 1 and compare. If p95 latency drops, keep the change; if it does not, revert and try the next lever. Do not keep configuration that does not move the measured numbers.

For UDP-free, connection-heavy workloads, consider WebSocket endpoint tuning (`perMessageDeflate`, ping intervals) and watch the event loop with a periodic microtask deadline check:

```typescript
const startedAt = performance.now();
// inside a hot loop
if (performance.now() - startedAt > 4) {
  await new Promise((resolve) => setTimeout(resolve, 0)); // yield to the event loop
  startedAt = performance.now();
}
```

### Step 5: Optimize the Production Bundle

Shape the artifact your deployment actually runs. For a Bun server, a compiled binary is the endgame; for other contexts, tune the JS bundle.

```bash
# Standard server bundle
bun build src/index.ts --target=bun --minify --sourcemap=external -o dist/index.js

# Drop debug statements and inline env values
bun build src/index.ts --target=bun --minify --drop=console,debugger --env-inline -o dist/index.js

# Standalone executable with bytecode
bun build src/index.ts --compile --minify --bytecode --target=bun -o dist/server
```

Verify with a bundle report that nothing absurd is being included:

```bash
bun build src/index.ts --target=bun --minify > /dev/null && ls -lh dist/
```

If the output is unexpectedly large, check for accidentally bundled dependencies (`--external`), duplicated modules from incompatible versions, and missing `--drop`. Re-run startup timing after the change; the compiled binary's cold start is measured in tens of milliseconds.

### Step 6: Reduce Startup and Cold-Start Time

Walk the entry path and remove work. Start with the expensive, rarely used imports and convert them to lazy `import()`. Remove top-level side effects that run on module load — a `setInterval`, a connection pool opened at import time, a config file read at the top of the entry module — and run them inside an explicit `start()` function instead.

```typescript
// Before: everything initializes at import time
import { connect } from './db.ts';
const db = connect(); // connects on every module load, even for CLI --help

// After: initialization is explicit and lazy
let db: ReturnType<typeof import('./db.ts')['connect']> | undefined;

export function getDb() {
  db ??= connect();
  return db;
}
```

Set `NODE_ENV=production` in the deployment environment so Bun skips dev-mode work, and measure cold start again with a timer:

```bash
/usr/bin/time -v ./dist/server --help
```

Compare the before/after numbers against the Step 1 baseline file. Startup optimization compounds: a server that starts in 40 ms scales out faster and costs less in serverless billable time.

### Step 7: Optimize Data Access and Hot Paths

Apply the hot-path rules where they pay the most: data access and request handling. With `bun:sqlite`, prepare statements once and reuse them, keep WAL mode on, and batch writes inside transactions.

```typescript
// Reuse prepared statements — never re-prepare per request
import { Database } from 'bun:sqlite';

const db = new Database('app.db', { create: true });
db.exec('PRAGMA journal_mode = WAL;');

const getItem = db.query('SELECT * FROM items WHERE id = ?1');
const insertItem = db.query('INSERT INTO items (id, name, price) VALUES (?1, ?2, ?3)');

export function findItem(id: string) {
  return getItem.get(id);
}

export function createItem(id: string, name: string, price: number) {
  insertItem.run(id, name, price);
}
```

For payload-heavy routes, prefer streaming over buffering, parse the body once, and avoid per-request allocations that escape to the heap. Then re-run the benchmark suite and the load test. The numbers tell you whether the hot-path cleanup worked.

### Step 8: Verify, Compare, and Lock In the Gains

Every optimization so far is a hypothesis tested against the baseline. Now formalize it.

```bash
# Re-run the exact baseline commands
bun test --bench benchmarks/items.bench.ts
oha -z 30s -c 100 -m GET http://localhost:3000/api/items > after-optimization.txt
```

Compare `after-optimization.txt` with `baseline-oha.txt` and update `PERFORMANCE.md` with the final numbers, the changes that produced them, and any trade-offs (for example, bytecode binaries trade disk size for startup speed). Then lock the gains in CI:

```yaml
# .github/workflows/performance.yml
name: Performance Gates
on: [pull_request]
jobs:
  benchmarks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - run: bun test --bench benchmarks/ --timeout 30
```

Add a bundle-size budget check and, when your deployment supports it, a cold-start budget. From this point on, a regression in the measured metrics blocks the merge, and the repository's performance story is written down, reproducible, and permanently enforced.
